# 首页左右滑动换日：需求评估

2026-10-27原评估；2026-10-28续作：用户指出左右换日未实现后，本项已纳入当前源码修订并本地实现，尚未打包到手机。用户同时明确移除首页下拉刷新、保留自动更新，覆盖下文原建议中的“保留下拉刷新”。当前实施与验证见 `UI_HOME_DATE_UNIT_IMPLEMENTATION.md`。

## 需求与建议

用户希望在首页左右滑动切换前一天、后一天，便于快速查找相邻日期。建议作为现有日期操作的快捷方式：左滑后一天，右滑前一天，一次手势只切一天；保留日期箭头、日期选择器和“今天”。跨较远日期继续使用日期选择器。

只在首页主要内容区（热量总览、四餐列表及其空白处）识别明显水平滑动。顶部日期/操作区、底部导航和子页面不加入手势。按钮普通点击仍按原功能执行；从按钮处开始的拖动应取消点击，避免翻日后误开添加页。加载状态也需一致处理，避免连续滑动出现忽然无效。

区分水平和垂直意图，短距离移动不换日；阈值需按真实手机校准，不写死未经验证的体验结论。纵向滚动、下拉刷新继续使用现有控件。尊重Android屏幕边缘返回区域；读屏保留可访问的日期按钮，无需依赖滑动操作。

## 实现依据和风险

当前首页已有上一天/下一天按钮，日期选择最终进入同一个加载方法，添加食品也携带所选日期。因此可复用现有日期操作，不需要改变存储格式或引入新的页面缓存/翻页动画。

已有“结果日期仍等于当前日期才显示”的保护，但它不能独自证明快速往返加载安全。例如A→B→A时，较早的A查询也可能通过日期判断。实施时需用延迟和乱序返回测试确认，必要时给每次加载编号，只接受最新请求；检查刷新和从子页面返回的共同调用路径，避免只修滑动入口。

风险集中在手势误识别、系统返回冲突、快速加载显示旧记录，以及换日后立即添加时日期归属错误。应按日历日期增减，沿用现有“一天开始于”规则，不按24小时或再次偏移来换日。未来日期的既有能力不擅自禁止；日期选择器边界和箭头/手势边界需一致，不能在边界处让选择器报错。

## 实施后的验证门槛

- 左右方向、单次只换一天、短拖动及斜向/纵向拖动不误触；按钮点击和下拉刷新保持可用。
- 快速连续换日、反向滑回、加载中再次操作、子页面返回，日期与四餐内容一致。
- 换日后立刻添加、修改、复制记录，目标日期/餐次正确，历史数据不变。
- 空记录日、未来日、跨月/跨年/闰日、非零换日时间以及日期边界。
- 真机系统边缘返回、长列表和大字体；本地测试通过不能代替实际手感验收。

原评估结论：可以做成小范围增强，但不能在实现和验证前承诺绝对没有影响。后续已进入源码实施与回归阶段；原评估不代表新版已装入手机。
