# M1 工作安排（已于 2026-10-15 开始，第四版核心原型已验收）

## 阶段边界

用户要求每阶段验收后再进入下一阶段。用户随后确认免费数据加手动补充的范围，并明确要求继续推进开发，因此已进入 M1，产出见 [设计提案](M1_DESIGN.md)和 [验证记录](M1_VALIDATION.md)。本文件保留原始工作安排；正式 Flutter 编译/测试和真机交互仍未验证，详见 M0_AUDIT.md，不能与浏览器原型测试混同。第四版核心原型现已获用户本轮验收；M2开始前仍需补齐本机运行基线，SDK暂不安装的限制继续有效。

## 建议顺序与交付

1. **需求矩阵与信息架构**：把所有要求映射到现有能力、M2 展示改造、M3 数据能力和 M4/M5 验收。页面涵盖首次使用、当日记录、历史日记、搜索/扫码/无结果、详情/改量/删除/重复添加、自建/修正版/我的食品、收藏、配方、趋势、个人资料/目标、设置/来源/隐私、备份恢复。活动、水和禁食已有功能的入口保留范围另行确认。
2. **核心流程图与页面状态**：先用搜索→核对来源和基准→输入摄入量→餐次保存做主线；补齐找不到、数据缺失、修正另存、离线/慢网/错误、编辑旧记录、撤销删除、恢复冲突。避免一个状态一个弹窗，日期和餐次贯穿操作。
3. **两种风格的局部对照**：先做同一首页/食品行的两种方向，比较信息密度和可读性，不一次画大量完整方案。可讨论方向为紧凑清晰的浅色界面、温暖中性色界面；颜色和名称都不是已选方案。
4. **统一设计系统**：确定主题/辅助/语义色及深色对照，中文字体与数字层级，间距、圆角、按钮/卡片/输入、单一图标体系和食品图片尺寸。Android 触控区域、系统返回、键盘与大字号作为设计约束。
5. **四页可预览原型**：首页、食品搜索、食品详情、食品编辑（简单/高级），支持日期/餐次切换、搜索模拟、查看来源、调整量实时更新、示例保存/修改/删除/重复添加。模拟数据明确标识，不冒充已接入接口或落盘。
6. **设计验收与修改**：提供真实预览截图，注明原型范围和未实现行为。按核心场景逐条走完，说明方案优缺点，用户提出意见并确认。确认后才制定 M2 小模块实现顺序。

## 重要取舍需要用户决定

| 决策 | 比较方案 | 评价方法 |
| --- | --- | --- |
| 首页能量区 | 紧凑数字/进度条；精简热量环 | 首屏可见餐次、目标/摄入/剩余是否易读 |
| “今天”与历史入口 | 合并日记；保留独立历史日记入口 | 改历史记录是否少绕路，导航是否重复 |
| 详情操作 | 同页固定底部摄入量和保存；局部底部面板 | 键盘弹起后是否遮挡营养和按钮 |
| 自建食品与当前入账 | 保存并继续记录；保存食品库后返回 | 必需输入项、点击数、是否误记当前餐次 |
| 个人核验 | 证据/核验时间后标“我已核对”；仅个人标记并明确未提供证据 | 不把自建、收藏、常用自动变成已核验 |
| 遥测/AI/水/禁食/健康同步 | 保留为可选；隐藏部分入口；移除具体服务 | 免费隐私承诺、维护成本和现有功能可用性 |

不在原型中用未经定义的星级/百分比“可信度”。来源、完整度、个人核对是不同属性；不能合成一个看似客观的分数。

## 尚需的信息

- 如果要准确借鉴或避开 YAZIO 的具体交互，需要用户实际使用版本的首页、搜索、详情和编辑截图，以及喜欢/不喜欢的具体操作。可先依据已明确的简洁和效率目标设计，但不能推定用户满意其全部页面。
- 最终 App 名称和图标尚未确定；原型先使用清楚标注的通用标题，不擅自确定品牌。
- 数据完整备份、个人核验字段、每100mL与重量换算，需要在 M1 给出显示和操作方案，在 M3/M4 完成存储与逻辑，不混入纯视觉修改。

## 原型验收场景

- 从任一餐次添加一种食品；名称、品牌、来源、基准、热量一眼可查。
- 输入 150 g 后正确显示示例营养倍率；每100mL食品使用其容量基准；每份显示换算依据，无依据时不编造重量。
- 无结果、无营养值、联网失败各有准确状态和自建入口。
- 公共食品修正另存，原来源可追溯；下次搜索自己核对的版本优先。
- 旧记录改量、删除、重复添加的目标日期/餐次明确。
- 简单/高级切换保持输入；缺失值和零区分；公式差异不强制覆盖热量。
- 深色、320/360/412 dp 宽度、键盘展开及大字体不遮挡主要操作。

正式实现阶段再执行 Flutter 组件/集成与真机验收；可点击原型只验收产品设计，不替代 App 数据测试。
